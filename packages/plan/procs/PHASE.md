# PHASE — a phase's work

A phase is a convergence milestone of ONE component of its plan: code, APIs or tests may break on the way; the plan converges clean at the end. A small undertaking is one phase with its batches, a large one several — the phase is never skipped, the batch below it is the only unit of work. Status and structure remain in `pp-plan`; only the method lives here. The phase document holds its SECTIONS, written by `pp-plan section` and never by hand: the CONTEXT (its brief, from the plan's Items line at birth), the GROUND, the TARGET, the EXPECTED, the ARBITRATIONS, the ITEMS — the batches prepared, one line each — and the DECISIONS, dated.

## The framing

The framing in force is the material. ZOOM OUT first, to Ground: read the ground whole — the sources, the code the phase will touch and its DEPENDENTS, so all enter the perimeter. Then BATCH the work: each batch is the LARGEST unit one turn can open, apply, verify and close — neither trivial nor unclosable; say for each whether it builds FROM SCRATCH or REFACTORS what stands — a refactor carries the alignment of every dependent, as its own batch or as todos of the batch that breaks them. Write Target (what the component becomes, what stays out) and Expected (what is true when the phase closes, each line with its rendering). Then PREPARE the batches as the lines of Items — `- slug -- brief`, the object, the OBSERVABLE exit and the proof mode in a sentence each; an entry per line, no document born: the operator amends a line until « frame » names the batch. LAST come the phase's laws and readings, derived from what the zoom-out read: the laws only where every batch of the phase can violate them, the serve rows carried by every batch — phase serve rows are REFERENCES grounding the level — specs, designs, contracts, maps — never code; code comes with the touching batch. A written law declares its SECTION: `constraints.production` for what the agent MAKES, proven at each checkpoint; `constraints.behavior` for what it does, says or reads, served every block and never proven. A plan document is a BLUEPRINT, not history: write the state TRUE now; retain only reasons and justifications from history, one dated line. The phase is `doing` once its Expected is written — and the agent STOPS: each batch is born on the GO that names it, by its first section.

## The work, on the GO

The operator's GO names the approved step. « frame X/p/b » births a prepared batch by its first section and frames it in the same turn; the phase's own prose is written by `pp-plan section`, never by hand. Questions, challenges or defects are served, never coded. When new work REVISITS what a closed batch established, rewrite its framing — a new todo in its Items, its Target — and the batch reopens (`redo`, the ancestry rises): its framing already carries the touched-and-dependent map — never create a twin; the component's history accumulates in its own document. The phase closes by the script in the call that delivers its last batch; statuses move by script as work arrives.
